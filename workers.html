Worker Architecture

Eight specialized workers (n8n workflows), each single-purpose. They never talk to each other — every handoff happens through status fields in the shared database.

Design rationale: many small workers are easier to diagnose than one big bot — when something breaks, the deal record and audit log show exactly which worker failed, at which gate, on which deal. But bot count alone doesn't create diagnosability; the shared database + append-only audit log do.

The Handoff Protocol

The single biggest fail point in a multi-worker system is a worker acting on stale or unvetted state. The protocol prevents it:

  1. Status fields are the handoff. Each stage of a deal carries a status field (e.g. intake_status: new → parsed → needs_human_verify → verified → released). A downstream worker only wakes when the status it subscribes to flips.
  2. Write immediately. A worker writes its results to the database in the same run, before doing anything else. No worker holds state privately.
  3. Re-read at execution time. A worker re-fetches the deal record the moment it acts — never acting on data it pulled earlier.
  4. Gates cannot be skipped. Statuses only advance in order; a worker cannot jump a deal past a gate it doesn't own.
  5. Everything logs. Every status change, gate pass/fail, and error appends to the Audit Log: timestamp, worker, deal, field, old → new, trigger.

The Gate List and Who Vets It (safest-approach configuration)

Gates are vetted by the Manager worker only where a written rule covers the scenario exactly; the human vets rule misses and everything marked human. Sensitive gates start human and are handed to the Manager only after a proven track record.

The Manager Worker & Rulebook (path to full automation)

The human approver evolves into a rulebook author: they write down how they handle every scenario and what they vet; the Manager worker applies those criteria mechanically.

  • Rulebook as data: a versioned table of rules (condition → action → authority). Example: "repair proposal ≤ $2,500 AND every item appears in the inspection report → approve."
  • Exact match or escalate: the Manager never interprets. If a scenario doesn't match a rule exactly, it escalates — a manager that "reads intent" recreates the single-mega-bot problem.
  • Audit stamp: every auto-approval logs "approved by Policy vN, rule X" — a stronger audit trail than a human click.
  • Learning loop (the safe ramp): the first deals run fully human-approved with every decision + reason logged; those decisions are distilled into rules; escalation rate falls with each deal (expect 30–50% escalations early; 80–90% auto-handled after ~30–50 deals).
  • Spot-check sampling: the weekly digest includes a random sample of auto-approvals for human review — a wrong rule fails silently and repeatedly, so sampling is the safety net.

Twilio SMS Escalation Ladder

When the Manager hits a rule miss (or any worker errors), the human is notified by text — SMS is the "pipeline is blocked" channel; email is for routine digests. n8n has a native Twilio node.

Rule miss / error→ Twilio SMS: deal + gate + Approval Queue link→ No response in N hours: re-ping→ Deadline horizon reached: deal auto-set On Hold + urgent SMS

An unanswered text can never silently let a deadline blow — the ladder ends in a hard stop, not a hope.

Deliberate trade-off: not every handoff is human-gated — with 30 active deals, a human gate on every step makes the approver the bottleneck and re-creates the manual process. Human involvement is reserved for the gates above, rule misses, and rulebook maintenance; everything else is machine-gated or Manager-vetted with full audit logging.

Worker Resources (rules, not guesswork)

Each worker operates from data, never improvisation:

  • SOP per worker — its role, allowed actions, escalation triggers ("company structure": what it does, why, and the edges of its job).
  • Rolodex tables — lenders, title companies, closing attorneys (county-mapped), inspectors, utilities.
  • TAR form catalog — RF-number vocabulary for classification and deadline events.
  • TN deadline rules — business-day roll-forward, federal holiday table, the RF654 event-driven resolution clock.
  • Templates library — every outbound email from an approved, branded template (logo, palette, disclaimer).
  • Rulebook — the versioned decision table the Manager worker applies; authored and signed off by the human.
  • Escalation matrix — one human queue (the Approval Queue) + the Twilio SMS ladder, not per-worker escalation paths.

Failure Handling

  • A worker error never silently drops a deal: errors write to the Audit Log and create an escalated task.
  • The On Hold / Blocked flag on a deal freezes all workers on that deal instantly.
  • A daily exceptions digest lists every deal stuck at a gate > N hours, every errored run, and every overdue task.
  • Any single worker can be switched off and its duties run manually from the database — the manual fallback is a design requirement, not an accident.
